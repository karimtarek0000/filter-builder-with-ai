# Phase 0 Research: Advanced Filter Builder

All Technical Context fields were resolvable directly (standard browser/React APIs on an already-clarified spec); no NEEDS CLARIFICATION markers remain. This document records the technical decisions and why simpler/alternative options were not chosen.

## 1. State management for the filter tree

- **Decision**: Local component state in `FilterBuilder.tsx` via `useState`/`useReducer`, holding the whole `FilterGroup` tree as one immutable value. Edits produce a new tree (structural sharing via spread/map, not mutation).
- **Rationale**: One page, one piece of state, one owner. A reducer keeps the "one edit → one new tree" invariant explicit (add/remove/update-condition, add/remove-group, toggle-and-or as actions) without pulling in a state library.
- **Alternatives considered**: Redux/Zustand/Jotai — rejected, no cross-component or cross-page state sharing exists to justify the dependency (Constitution III, YAGNI). Context API — rejected, the tree only needs to flow one level (`FilterBuilder` → `FilterGroup` → `FilterCondition`), so props are simpler and more explicit than context.

## 2. Filter tree node identity

- **Decision**: Every condition and group gets a stable `id: string` generated with `crypto.randomUUID()` when created, used as the React `key` and as the target for edit/remove operations.
- **Rationale**: `crypto.randomUUID()` is available in all evergreen browsers Vite targets by default, needs no dependency, and avoids index-based keys (which break identity across reorders/removals).
- **Alternatives considered**: An incrementing counter — rejected, requires a module-level mutable counter or context to stay unique across remounts (e.g., after a URL-driven reset), which `randomUUID()` avoids entirely.

## 3. URL encoding for the shareable filter

- **Decision**: Serialize the `FilterGroup` tree to JSON, then to a URL-safe base64 string using `btoa(encodeURIComponent(...))`-style handling (or an equivalent manual `+/` → `-_` substitution) so it can sit in one query parameter (e.g., `?f=<encoded>`) without further percent-escaping.
- **Rationale**: Matches the spec's clarified answer (FR-013/FR-014) exactly: single param, JSON + base64url. `btoa`/`atob` are built into the browser; no dependency needed. URL-safe substitution avoids `+`, `/`, `=` needing percent-encoding inside the query string. Per FR-013's 2026-07-28 clarification, `encodeFilterToParam` first drops any condition currently failing validation (§10) from the tree before running steps 2-4 below — see [contracts/filter-url-schema.md](./contracts/filter-url-schema.md) for the exact rule.
- **Alternatives considered**: A query-string-per-field encoding (e.g., `?f0=country&o0=is&v0=EG`) — rejected, can't express arbitrary nesting/groups cleanly and wasn't what was clarified. A querystring library (`qs`, `query-string`) — rejected, `URLSearchParams` plus `btoa`/`atob` already covers the one param this feature needs.

## 4. Reading/writing the URL without a router

- **Decision**: A single `useFilterUrlSync` hook: on mount, read `window.location.search` via `URLSearchParams`, decode+validate, and use the result (or an empty filter on failure) as initial state; on every filter change (via a `useEffect` keyed on the tree), re-encode and call `window.history.replaceState(null, "", url)`.
- **Rationale**: Matches the clarified requirement to replace (not push) history entries. No router is in the project and none is needed for one page.
- **Alternatives considered**: `react-router`'s `useSearchParams` — rejected, pulling in a router for one page and one param contradicts Constitution III/CLAUDE.md ("no router" is explicit in the spec's own framing).

## 5. Decode validation strategy (fallback to empty filter)

- **Decision**: `decodeFilterFromParam` returns `FilterGroup | null`. It never throws: base64/JSON failures, and structural validation against `fieldConfig` (unknown field, unknown operator for that field, wrong shape) all return `null`, which the caller treats as "empty filter." Input is typed `unknown` after `JSON.parse` and narrowed field-by-field — no `any`.
- **Rationale**: Directly satisfies FR-015/SC-005 ("never crash, always fall back") and Constitution VII (narrow `unknown` instead of `any` at this trust boundary).
- **Alternatives considered**: A schema validation library (`zod`, `valibot`) — rejected, the shape is small and fixed (two node kinds, five fields); hand-written narrowing functions in `urlState.ts` are fewer lines than adding and learning a new dependency for one call site.

## 6. Plain-language sentence generation

- **Decision**: A pure function `describeFilter(tree: FilterGroup): string` in `filterEngine.ts`, built from per-field/operator phrase templates in `fieldConfig.ts` (e.g., `country` + `is` → `"country is {value}"`), joined with `" and "`/`" or "` per group, with the nested group's phrase parenthesized.
- **Rationale**: Satisfies FR-012/SC-003 and keeps the phrasing rules colocated with the operator config that already drives the UI (Constitution I: adding a field's phrasing is one config entry, not new branching logic).
- **Alternatives considered**: Templating library — rejected, five fields and twelve operators total don't justify one.

## 7. Value input per field type

- **Decision**: `fieldConfig.ts` maps each `Field` to its allowed `Operator[]` and, per operator, a `valueKind` (`"text" | "number" | "select" | "day" | "month" | "year" | "none"`), plus (for `country`) the fixed option list `["EG", "SA", "AE", "US", "DE"]`. `FilterCondition.tsx` switches rendering on `valueKind`, not on the field name.
- **Rationale**: Directly implements FR-003/FR-004/FR-005 as data, matching Constitution VI (extension through configuration). `valueKind` is resolved per-operator (not per-field) because `hireDate`'s three operators each need a different input, unlike every other field where all operators share one input kind.
- **Alternatives considered**: Per-field components (`NameConditionRow`, `SalaryConditionRow`, ...) — rejected, would duplicate the shared field/operator/remove chrome across five near-identical components for no behavioral gain. Keeping `valueKind` at the field level and special-casing `hireDate` in `FilterCondition.tsx` — rejected, that reintroduces the field-name branching Constitution VI forbids; per-operator config keeps the component logic uniform.

## 8. Hire date storage and component extraction

- **Decision**: `Employee.hireDate` is a plain ISO `"YYYY-MM-DD"` string. Day/month/year components for matching are extracted by slicing the string (`hireDate.slice(0, 4)`, `.slice(5, 7)`, `.slice(8, 10)`), not by constructing a `Date` object.
- **Rationale**: `new Date("YYYY-MM-DD")` parses as UTC midnight; reading it back with `.getDate()`/`.getMonth()` uses the browser's local timezone, which can silently shift the day (and sometimes month) backward for timezones behind UTC. String slicing is timezone-free, needs no dependency, and keeps the static mock data trivially hand-authorable (FR-018, Edge Cases: independent day/month/year matching must be exact).
- **Alternatives considered**: `Date` + UTC getters (`getUTCDate`/`getUTCMonth`/`getUTCFullYear`) — would also avoid the timezone bug, but adds `Date` construction/parsing for no benefit over slicing a string whose format is already fixed and controlled. A date library (`date-fns`, `dayjs`) — rejected, three fixed-position substring reads don't justify a dependency (Constitution III).

## 9. Month selector values

- **Decision**: The `month_is` operator's value is a number `1`-`12` (matching the ISO string's month component), rendered as a `<select>` of month names (`"January"`…`"December"`) mapping to those numbers. The name list is a small constant colocated with `fieldConfig.ts`, not fetched or generated.
- **Rationale**: Satisfies FR-004/Scenario 5 (month must be picked from a selector, not typed as a free number) while keeping the stored `value` type unchanged (`string | number | undefined` — no widening of `FilterCondition.value`, Constitution VII).
- **Alternatives considered**: Storing the month as its name string (`"March"`) — rejected, forces string-to-number translation back at comparison time for no gain, since the underlying data is numeric (`"YYYY-MM-DD"`).

## 10. Condition-value validation (FR-021/FR-022, User Story 6)

- **Decision**: A new `validation.ts` module holds a Zod schema per `(field, operator)` pair, keyed the same way `fieldConfig.ts` keys `valueKindByOperator` (e.g., `salary`'s `gt`/`lt`/`eq` → `z.coerce.number().nonnegative()`; `hireDate`'s `year_is` → a 4-digit-integer schema; text/select fields → a non-empty-string or enum schema; `is_true`/`is_false` → no schema, always valid). It exports one function, `validateConditionValue(condition): { valid: true } | { valid: false; error: string }`, used by both `FilterCondition.tsx` (to render the inline error, FR-022), `filterEngine.ts`'s `evaluateNode` (to treat an invalid value as vacuous/unset for matching, Edge Cases), and `urlState.ts`'s `encodeFilterToParam` (to drop an invalid condition from the tree before it's serialized, per the 2026-07-28 clarification recorded in FR-013 and [contracts/filter-url-schema.md](./contracts/filter-url-schema.md)). This is a distinct trust boundary from §5's URL-decode validation: §5 validates untrusted `unknown` JSON structure once, at load time; this validates a trusted, already-typed `string | number | undefined` value the user is actively typing, on every keystroke, for user-facing feedback — different problem, different tool.
- **Rationale**: Directly implements FR-021's requirement for "a declarative, schema-based validation approach," matches the spec's Assumptions (which name Zod explicitly as a deliberate, narrow exception to "no implementation details" — see spec.md Assumptions and checklists/requirements.md), and Zod is already a project dependency (`package.json`), so no new dependency is introduced. Centralizing rules in one schema map keeps "add a field's validation rule" a one-entry change (Constitution I, VI) instead of new `if` branches in `FilterCondition.tsx`.
- **Alternatives considered**: Hand-written per-field validator functions (matching §5's approach for URL decoding) — rejected here specifically because FR-021 explicitly calls for a *schema-based* approach and the spec's Assumptions name Zod as the intended tool; unlike §5's small, fixed, one-call-site JSON shape, this validation set is per-operator, user-facing, and growing (Stories 1–7 already imply 8+ distinct rules), which is exactly where a schema library's declarative composition earns its keep over hand-rolled `if`s.

## 11. Salary and hire-date display formatting (FR-019/FR-020, SC-009)

- **Decision**: A new `format.ts` module exports two pure functions: `formatSalary(salary: number): string` using `Intl.NumberFormat` (locale default, `maximumFractionDigits: 0`) for thousands-separated, no-decimal, no-currency-symbol output (e.g., `85,000`); and `formatHireDate(hireDate: string): string` that builds `"D MMM YYYY"` (e.g., `2 Jun 2026`) by slicing the same `"YYYY-MM-DD"` components used for filtering (§8) and mapping the month number to its 3-letter abbreviation via a small constant — never by constructing a `Date` object, for the same timezone-drift reason as §8.
- **Rationale**: FR-019/FR-020 are presentation-only and must never affect the underlying `salary`/`hireDate` values used for filtering or URL encoding (spec.md Key Entities); keeping formatting in dedicated pure functions (Constitution V) called only from `EmployeeTable.tsx` guarantees that. Reusing §8's string-slicing approach (instead of `Date` + `Intl.DateTimeFormat`) avoids reintroducing the exact timezone bug §8 already ruled out, and keeps one date-reading strategy for the whole feature (Constitution I: one rule, one place).
- **Alternatives considered**: `toLocaleString()` for salary — rejected, its output format depends on the runtime's default locale in a way `Intl.NumberFormat` with explicit options does not, and this feature has no locale requirement beyond "consistent" (SC-009). `Intl.DateTimeFormat` for the hire date — rejected for the timezone reason above; a date library (`date-fns`, `dayjs`) — rejected, one fixed input format and one fixed output format don't justify a dependency (Constitution III), consistent with §8's same conclusion.

## 12. Condition alignment and nested-group distinction (FR-023/FR-024, User Story 7)

- **Decision**: `FilterCondition.tsx`'s field/operator/value/remove controls are laid out with a fixed-width Tailwind grid (`grid grid-cols-[...]` with explicit column widths, applied identically to every condition row so a group's rows line up regardless of which `valueKind` each row is currently rendering). `FilterGroup.tsx` renders a nested group (`isRoot={false}`) with an added left border and indentation (e.g., `border-l-2 pl-4 ml-2`) that the root group does not get.
- **Rationale**: Satisfies FR-023 (columns must align across varying value-input kinds, which render different control types) and FR-024/SC-008 (a nested group must read as visually distinct without reading the sentence) using only Tailwind utility classes already available in the project — no new dependency, no new component, matching Constitution III/V.
- **Alternatives considered**: A `<table>`-based layout for conditions — rejected, conditions aren't tabular data with a header row, and CSS grid on the existing `div`-based rows achieves the same column alignment with less structural change (Constitution IV: surgical, not a rewrite of `FilterCondition.tsx`'s element structure). Per-`valueKind` fixed pixel widths passed as props — rejected, that's branching logic where a shared grid template column list is simpler and already colocated in one place.

## 13. Debounced re-evaluation for free-text/numeric values (FR-011 amended, FR-025, User Story 1 Scenario 5)

- **Decision**: Whether a `valueKind` debounces is one more boolean fact on the same `fieldConfig.ts` entry that already selects its input control — `text`/`number`/`day`/`year` → debounced, `select`/`month`/`none` → immediate (they don't fire per keystroke, so there's nothing to debounce). `FilterCondition.tsx` holds the in-progress value in local `useState` so the input itself never lags, and commits it to the parent tree (via `onChange`) inside a `useEffect`-scheduled `setTimeout(..., 300)` that resets on every keystroke; immediate `valueKind`s call `onChange` synchronously as before, unchanged.
- **Rationale**: FR-025 requires debouncing scoped to specific input kinds, not the whole tree — debouncing at the tree level (e.g., in `FilterBuilder.tsx` or `useFilterUrlSync`) would also delay selection-based edits, which FR-025 explicitly forbids. Keeping the debounce local to `FilterCondition.tsx` and driven by the same config flag that already picks the input control keeps this "add one more `valueKind` fact," not new branching (Constitution VI), and needs no new file — a `useState`+`useEffect`+`setTimeout` in the one component that owns the keystrokes is simpler than a shared hook with exactly one caller (Constitution III).
- **Alternatives considered**: A generic `useDebouncedValue` hook in its own file — rejected, it would have exactly one call site (`FilterCondition.tsx`), so extracting it is premature abstraction (Constitution III: "a utility nothing calls yet → don't write it" applies equally to one a second caller doesn't yet exist for). Debouncing `matchCount`/table evaluation centrally (e.g., wrapping the whole filter tree in a debounced value before `filterEngine` runs) — rejected, it can't distinguish "this edit came from a text input" from "this edit came from a dropdown," so it would either debounce everything (violating the "selection inputs stay immediate" half of FR-025) or need the same per-`valueKind` flag threaded back in anyway, with an extra indirection layer for no benefit. A debounce library (`lodash.debounce`, `use-debounce`) — rejected, one `setTimeout`/`clearTimeout` pair is simpler than a new dependency for a single 300ms delay (Constitution III).

## 14. Mobile remove-control placement (FR-026, User Story 8)

- **Decision**: `FilterCondition.tsx`'s existing fixed-column grid (§12) switches to a single-column stacked layout below Tailwind's `md` breakpoint (`grid-cols-1 md:grid-cols-[10rem_8rem_12rem_5rem]`), so the remove control lands on its own row on narrow viewports without any separate markup, JS-based viewport detection, or a second remove button. At `md` and above, the existing fixed-column grid (and the remove control's inline placement within it) is unchanged.
- **Rationale**: FR-026 only requires the remove control not crowd the field/operator/value inputs below `md`, and to be unchanged at `md`+ — a responsive grid-column-count change is a pure CSS layout decision (Constitution IV: surgical, touches only the class list already on this row) and reuses the same grid element from §12 rather than adding a second, mobile-only remove button or a `useMediaQuery`-style JS breakpoint check (which would need a dependency or hand-rolled `resize` listener neither of which the spec's "outside the row" requirement calls for).
- **Alternatives considered**: A duplicate remove button toggled with `hidden`/`md:hidden` pairs — rejected, two DOM nodes for one control is more moving parts than one grid that already reflows; CSS handles this without any conditional rendering. A JS `matchMedia`/resize-listener check to conditionally render a different layout — rejected, Tailwind's existing breakpoint convention (already used elsewhere in this project, per spec.md Assumptions) does the same thing declaratively with no extra state or effect.

## 15. Extracting the debounce mechanism into one hook (FR-027, FR-028, SC-012, User Story 9 — amends §13)

- **Decision**: Extract the debounce logic currently inlined in `FilterCondition.tsx` (a `conditionRef`, a `localValue` state, a `syncedValue` state, and two `useEffect`s — see the shipped implementation from §13) into a single new file, `useDebouncedValue.ts`. The hook takes the externally-committed value, a commit callback, and the delay, and returns the value to display plus the change handler; it owns re-sync (external value changed → adopt it) and commit-after-pause (local edit → call back after the delay) as one cohesive unit. `FilterCondition.tsx` calls it once per debounced `valueKind` and no longer holds any debounce-related state itself. Non-debounced `valueKind`s bypass the hook's delay path entirely, unchanged from §13.
- **Rationale**: §13 rejected a standalone hook because it would have exactly one caller, making extraction premature under Constitution III. User Story 9 changes the input to that trade-off, not the trade-off itself: FR-027 now explicitly requires this mechanism to be "a single, clearly-named unit of logic," and the spec's Assumptions name a custom hook as a deliberate, narrow implementation hint at the user's explicit request — the same precedent already used for Zod and the base64url URL scheme. Per CLAUDE.md's Code Principles ("When two rules conflict, the section that comes first wins"), Readability precedes Scope, and the shipped §13 implementation is exactly the readability failure Readability's "test" describes: the debounce invariant (immediate display, delayed commit, correct re-sync) is spread across three state variables and two effects that must be read together to verify, not one named place. Extracting it removes that "single caller" YAGNI objection without weakening it as a general rule — it applies here only because the spec now requires the extraction directly, not speculatively.
- **Alternatives considered**: Leave the logic inlined and only rename/comment it for clarity — rejected, FR-027's acceptance scenario (US9 Scenario 1) requires the mechanism to be expressed as "one hook," not merely well-commented; comments don't satisfy "a single, clearly-named unit of logic" when the state is still distributed across the component. A generic debounce library (`use-debounce`) — rejected for the same reason as §13: one small hook local to this feature is simpler than a new dependency, and FR-027 asks for the mechanism to be self-contained and readable, not for it to be outsourced. Making the hook generic/reusable beyond this one call site (e.g., accepting arbitrary comparison functions or multiple values) — rejected, only one caller exists today (`FilterCondition.tsx`); Constitution III still governs the hook's *internal* generality even though the extraction itself is now required.
- **Behavior preservation (FR-028)**: The hook must reproduce §13's externally-observed behavior exactly — typed keystrokes shown immediately, `onChange` committed once after a pause in typing (not per keystroke), non-debounced `valueKind`s update synchronously, and local edit state re-syncs to an externally-changed `condition.value` (e.g., switching fields clears the value) without stale or duplicate state. This is a refactor of §13's implementation, not a change to the decision recorded there.

## 16. Condition-row logic consolidated into one hook (FR-029, FR-030, SC-014, User Story 10)

- **Decision**: Add `useConditionRow.ts`, a hook that owns everything `FilterCondition.tsx` currently computes or handles inline — reading `fieldConfig`/`valueKindForOperator` for the current field/operator, running `validateConditionValue`, calling `useDebouncedValue` for debounced `valueKind`s, and the field-change/operator-change/value-change handlers (FR-005's reset-on-field-change and reset-on-hireDate-operator-change rules included). It takes `(condition, onChange)` and returns a single object — `{ config, valueKind, displayValue, validation, handleFieldChange, handleOperatorChange, handleValueChange }` — that `FilterCondition.tsx` destructures and renders directly, with no computation of its own left in the component body.
- **Rationale**: FR-029 requires field-change, operator-change, and value-commit handling to be "owned by a single custom hook," with the component "limited to rendering based on the values and handlers that hook returns" — that's a direct requirement, not a judgment call. It also resolves FR-030: today `handleValueChange` contains `if (debounced) { setLocalValue(value) } else { onChange(...) }`, an inline conditional keyed on a config-derived boolean. Moving that branch inside the hook and replacing it with a per-`valueKind` commit-strategy lookup (§17's sibling concern — see below) satisfies "driven by field/operator configuration data... not a conditional branch written inline in the component or its hook" everywhere except the one place a strategy has to be selected, which by definition must read the map once.
- **Alternatives considered**: Splitting the hook into two (one for field/operator handling, one for value/debounce handling) — rejected, `FilterCondition.tsx` has exactly one condition row to manage and Constitution III ("no caller yet") applies in reverse here: two hooks for one component's one set of concerns is the scattering Principle I warns against ("a clear unit MUST NOT be split into small, scattered pieces merely for the sake of decomposition"). Leaving `handleValueChange`'s `if (debounced)` branch as-is and only extracting the other handlers — rejected, FR-030 specifically targets that branch, not just the general shape of the hook.
- **Commit-strategy dispatch (FR-030 detail)**: replace the inline `if (debounced) {...} else {...}` with a two-entry map keyed by the same `boolean` `isDebouncedValueKind` already exposes — `{ true: (setLocal, value) => setLocal(value), false: (commit, value) => commit(value) }` — or equivalently, since there are exactly two outcomes and the map has no room to grow (a value is either staged or committed, nothing else), inline the two calls as `debounced ? setLocalValue(value) : onChange({ ...condition, value })` **inside the hook** where FR-030 permits it, as long as `debounced` itself is never re-derived by name-checking `field`/`operator`/`valueKind` — it must always come from `isDebouncedValueKind(valueKind)`, the existing config lookup. This keeps a genuine two-way binary decision as a ternary (Constitution VI's gate targets `if`s comparing against a *domain value* — a field/operator/valueKind name — not a boolean already sourced from config) while still satisfying FR-030's actual concern: the *debounced-or-not* fact must come from configuration, not be hardcoded per field.

## 17. Value-input control resolved through a lookup map (FR-031, SC-015 — already implemented as `ValueInput.tsx`)

- **Decision**: `ValueInput.tsx` exports a `Record<ValueKind, (props: InputProps) => JSX.Element | null>` map (`inputsByValueKind`) holding one small presentational component per `ValueKind` (`text`, `number`, `select`, `day`, `month`, `year`, `none`), plus a thin `ValueInput` wrapper that looks up and renders the right one. `FilterCondition.tsx` renders `<ValueInput valueKind={valueKind} .../>` and contains no `if`/`switch` on `valueKind`, `field`, or `operator` of its own.
- **Rationale**: Matches FR-031 exactly ("resolved through a single lookup map... no per-field or per-value-kind conditional rendering of its own") and SC-015 (a new value kind is one map entry, not a new branch). This is the same "map keyed by type, behavior held in the map" pattern Constitution VI already mandates for 3+ growing branches — `ValueKind` has seven variants today and is exactly the kind of enumerable, config-shaped variation the constitution says must not be `if`-chained in a component.
- **Alternatives considered**: A single generic `<input>` with `type` computed from `valueKind` — rejected, `month` needs a `<select>` of named options and `select` needs a caller-supplied option list, so one generic element can't cover every kind without smuggling a conditional back in via a `type` prop that fans out downstream anyway. Keeping per-kind rendering as a `switch` statement inside `FilterCondition.tsx` — rejected, that's exactly the "conditional rendering... in the component" FR-031 rules out; a map is a value, a `switch` is branching logic, even though both are exhaustive over the same union.

## 18. Top-level filter page as pure composition (FR-032, SC-014, User Story 11)

- **Decision**: `FilterBuilder.tsx` keeps only `useFilterUrlSync()` (state) and `filterEmployees(root, employees)` (a call to existing `filterEngine.ts`), and renders `<FilterGroup>` / `<EmployeeTable>` plus the match-count sentence. The match-count text itself — today inlined as a JSX-embedded pluralization (`` `${n} match${n === 1 ? '' : 'es'}` ``) — moves into a new plain function, `describeMatchCount(count: number): string`, in `filterEngine.ts` (alongside the existing `describeFilter` sentence generator it sits next to conceptually). `FilterBuilder.tsx` calls `describeMatchCount(visibleEmployees.length)` and renders the result; it computes no string itself.
- **Rationale**: FR-032 requires the top-level component to contain "no logic beyond composing its child components and calling hooks/functions defined elsewhere," naming the pluralized match-count message as the explicit example of derived text that must move out. `filterEngine.ts` already owns the sibling responsibility (`describeFilter`) and has no framework imports (Constitution V), so adding one more small pure function there is "one more of an existing thing" (Principle I's test) rather than a new file for a single string.
- **Alternatives considered**: A new `formatMatchCount.ts` file — rejected, one two-line function doesn't justify a new module when `filterEngine.ts` already exports sibling formatting/description logic with no framework dependency (Constitution III: no file for a utility that fits an existing one just as well). Leaving the pluralization inline but extracting only the `visibleEmployees.length` computation — rejected, FR-032's acceptance scenario is explicit that *any* text formatting or data derivation, not just filtering, must live outside the component.

## 19. Debounce hook relocated to a shared, project-level module (FR-033, FR-034, SC-013, SC-016, User Stories 12-13)

- **Decision**: Move `useDebouncedValue.ts` out of `src/features/filter-builder/` to `src/hooks/useDebouncedCommit.ts` (renamed to describe what it does generically — commit a value after a pause — rather than a filter-specific "debounced value"), with a `src/hooks/index.ts` that re-exports it as the module's sole public symbol. `filter-builder`'s `useConditionRow.ts` (§16) imports it from `../../hooks` (the new module's entry file), never from the nested file directly. The hook's signature and behavior are unchanged from §15 — it already took a generic `(value, onCommit, delayMs)` and returned `[localValue, setLocalValue]`, with no filter/condition/field concept baked in, so relocation is a file move plus an import-path update, not a rewrite.
- **Rationale**: FR-034 requires the mechanism to live outside `filter-builder` as a generic, reusable wrapper with no filter-specific references — true today of the hook's *implementation*, just not its *location* or *name* (`useDebouncedValue` reads as filter-specific even though it isn't). FR-033 requires every module, including this new one, to expose its public API through a single entry file that no internal file imports back from — `src/hooks/` becomes a second module under that same rule (Constitution VIII), alongside `filter-builder`'s existing `index.ts` (already compliant, per the Constitution Check in plan.md). SC-013 requires an unrelated feature to use it "without... learning any filter-specific concept" — true structurally today, but only true *discoverably* once it's outside the feature folder a stranger has no reason to open.
- **Alternatives considered**: Keep the hook inside `filter-builder` and just export it from that feature's `index.ts` for outside use — rejected, that widens `filter-builder`'s public API (Constitution VIII) to include a concern that has nothing to do with filtering, and violates FR-034's explicit "relocated to a shared, project-level location outside the `filter-builder` feature." A generic `src/lib/` or `src/utils/` catch-all directory — rejected in favor of `src/hooks/`, since the thing being shared is specifically a React hook (a category the project doesn't yet have a home for) and `hooks/` names that category precisely rather than becoming an undifferentiated dumping ground; Assumptions in spec.md leave the exact directory name to planning, and `src/hooks/` is the smallest, most conventional choice for "a hook, shared, outside any feature."
- **Module boundary check (FR-033)**: `src/hooks/index.ts` exports `useDebouncedCommit` only; no file inside `src/hooks/` imports from `src/hooks/index.ts` itself (mirroring the same check already applied to `filter-builder/index.ts`); no wildcard re-export.

## 20. Clear All control (FR-036, FR-037, SC-017, User Story 14)

- **Decision**: One new plain function, `createEmptyFilter(): FilterGroup`, in `filterEngine.ts` (`{ id: crypto.randomUUID(), kind: "group", logic: "AND", children: [] }` — the same shape §2/§11 already use for a freshly-created group). `FilterBuilder.tsx` renders one always-visible "Clear All" button that calls its existing filter-tree setter (the same one every add/edit/remove already calls, from `useFilterUrlSync`) with `createEmptyFilter()`. No new state, no new effect, no confirmation dialog/modal.
- **Rationale**: FR-036/FR-037 require one control that resets the whole tree and immediately updates rows/count/sentence/URL — since every other edit already flows through one setter that triggers re-evaluation, re-encode, and `replaceState` (§4), Clear All only needs to call that same setter with a fresh empty tree; no separate "clear" code path is needed. Keeping it a plain function next to `createCondition`/`createGroup`-style helpers (rather than inlining the literal in `FilterBuilder.tsx`) keeps `FilterBuilder.tsx` as pure composition (FR-032) — the button wires an existing handler to an existing function, it doesn't construct anything itself.
- **No-op-when-empty (FR-037)**: not special-cased — setting the tree to a new `createEmptyFilter()` when it's already an empty root group produces the same rendered state (same shape, different `id`), so "no visible effect" falls out of the existing re-render behavior rather than needing an `if (isAlreadyEmpty) return` guard (Constitution VII: no runtime check for a case the existing behavior already covers correctly).
- **Alternatives considered**: A dedicated `clearFilter` action/reducer case distinct from "set tree" — rejected, there's already exactly one state-update path (§1's reducer or setter) and every edit (add/remove/toggle) already goes through it with a new tree value; Clear All doesn't need a distinguishable action type since nothing downstream (URL sync, re-evaluation) needs to know an edit was specifically a "clear" versus any other tree replacement. A confirmation dialog before clearing — rejected, spec.md Assumptions explicitly call this out as unnecessary given the low cost/reversibility of the action (an already-shared URL can be reloaded to restore the prior filter).

## 21. Multiple nested groups inside the root (FR-007, FR-008 revised, User Story 3 Scenario 2, 2026-07-28 Amendment)

- **Decision**: No type-level change — `FilterGroup.children` (data-model.md) already permits any number of `FilterGroup` elements structurally; only the runtime-enforced count changes, from "reject a second nested-group child" to "no count limit on nested-group children, only a depth limit." `FilterGroup.tsx`'s "add group" control is available whenever the group being rendered is the root (`isRoot === true`), unconditionally — the earlier `children.filter(c => c.kind === "group").length === 0` guard is removed entirely rather than raised to a higher number. Each nested group continues to reject its own "add group" control (`isRoot === false` never renders it), which is what keeps the tree at two levels regardless of how many nested groups the root holds.
- **Rationale**: FR-007's revised text ("MAY hold any number of nested groups") and Story 3 Scenario 2 require the add-group control to stay available after the first nested group exists — an unbounded count is a *simpler* rule than the count-of-one it replaces (one fewer condition to check), not a more complex one, so removing the guard rather than parameterizing it (e.g. a `maxNestedGroups` config value) matches Constitution III: no configurability for a limit the spec doesn't ask for. `describeFilter` (§6) and `evaluateNode` (data-model.md) already iterate `children` generically via `.map`/`every`/`some`, so going from "at most one nested-group child" to "any number" requires no change to either function — the existing generic tree-walk already handles it.
- **Alternatives considered**: Introducing a `maxNestedGroups` constant checked against `children.filter(...).length` — rejected, "any number" is the spec's literal answer (2026-07-28 Amendment), so a configurable cap would be unused configurability (Constitution III: "no config options... for features that don't exist yet"). Distinguishing "first nested group" from "subsequent nested groups" in rendering (e.g., different styling for the second one) — rejected, spec.md's Assumptions state the visual distinction (FR-024) applies uniformly to every nested group, so no per-instance branching is needed.

## 22. Accessibility: keyboard operability and assistive-technology labels (FR-038, SC-018)

- **Decision**: No new components or state. Every interactive element already used in `FilterGroup.tsx`/`FilterCondition.tsx`/`ValueInput.tsx`/`FilterBuilder.tsx` is a native HTML control — `<button>` for add/remove/Clear All, `<select>` for `country`/operator/month dropdowns, `<input>` for text/number/day/year — all natively keyboard-operable (Tab to focus, Enter/Space to activate, arrow keys within `<select>`) with zero custom key-event handling required. Labeling: every `<select>`/`<input>` gets a visible `<label>` (preferred, since it also benefits sighted users scanning the row per FR-023) or, where a visible label would break the row's alignment (e.g., an icon-only remove/add-group button), an `aria-label` describing the action (e.g., `aria-label="Remove condition"`, `aria-label="Add nested group"`). No `aria-live` region is added for match-count or validation-error updates — FR-038 explicitly excludes live/spoken announcements from scope.
- **Rationale**: FR-038 requires keyboard operability and clear assistive-technology labels, not a from-scratch accessible-widget implementation — since every control in this feature is already a plain native form element (no custom dropdown, no drag-and-drop, no custom combobox), the browser's built-in keyboard/AT support already satisfies the operability half of FR-038 for free; the only real work is ensuring labels exist. Explicitly excluding `aria-live` regions (the requirement's own carve-out) avoids the one part of this feature (frequent match-count/validation updates on every keystroke) that would otherwise need careful `aria-live="polite"` debounce-coordination to not spam a screen reader — SC-018 only requires *identifying a control's purpose*, not being notified of every re-evaluation.
- **Alternatives considered**: A custom-styled `<select>` replacement (e.g., a `<div role="listbox">` combobox) for the field/operator/country dropdowns — rejected, would require hand-built keyboard handling (arrow keys, typeahead, `aria-activedescendant`) to reach the same operability a native `<select>` already has for free, adding real complexity FR-038 doesn't ask for (Constitution III). Adding `aria-live="polite"` to the match-count and inline-error regions — rejected, FR-038 explicitly says live/spoken announcements are not required, and per-keystroke error updates (FR-022) would otherwise need debounced announcement logic to avoid interrupting a screen reader user mid-typing, which is out of scope.

## 23. Generic `FilterFieldConfig<TRow>` replaces the hardcoded `Field`/`Operator` unions (FR-039, User Story 15)

- **Decision**: `types.ts`'s `Field`/`Operator` string-literal unions are replaced by `field: string` / `operator: string` on `FilterCondition`, validated at runtime against a caller-supplied `FilterFieldConfig<TRow>` object rather than checked at compile time against a fixed union. `FilterFieldConfig<TRow> = Record<string, FieldDef<TRow>>`, where `FieldDef<TRow> = { label: string; operators: Record<string, OperatorConfig<TRow>> }`, and `OperatorConfig<TRow> = { label: string; valueKind: ValueKind; options?: readonly string[]; schema?: ZodTypeAny; match: (row: TRow, value: unknown) => boolean; describe: (value: unknown) => string }`. Every function that today switches on a hardcoded `Field`/`Operator` — `evaluateNode`'s per-condition comparison, `describeFilter`'s phrase templates, `validateConditionValue`'s schema lookup, `ValueInput`'s control resolution — instead reads `fieldConfig[condition.field].operators[condition.operator]` and calls the `match`/`describe`/`schema` it finds there. `FilterBuilder` (and the components/engine functions it composes) become generic in `TRow`, accepting `fieldConfig: FilterFieldConfig<TRow>` and `data: TRow[]` as props.
- **Rationale**: FR-039 requires the engine, condition/group components, and validation to "operate against a field configuration and dataset supplied by the caller (via props/generics)," with "no file inside the feature" referencing Employee-specific field names, operators, or value-kind mappings. Moving `match`/`describe`/`schema` into the config object (instead of a `switch (field)`/`switch (operator)` inside the engine) is the same "behavior lives in the map, not in branching" pattern Constitution VI already mandates for `fieldConfig.ts`/`ValueInput.tsx` (§7, §17) — this section only widens *who supplies the map's contents* from "hardcoded inside the feature" to "passed in as a prop," without introducing a new kind of indirection the codebase doesn't already use.
- **Alternatives considered**: A discriminated union of known "table kinds" (`EmployeeConfig | OtherConfig`) selected by a prop flag — rejected, that's a second implementation for a hypothetical second table (Constitution VI: no interface without a second implementation), and the spec explicitly only requires the *shape* to be generic, not a second live consumer (spec.md Assumptions, Amendment 3). Keeping `Field`/`Operator` as compile-time unions but making them a generic type parameter (`Field<TConfig> = keyof TConfig`) threaded through every function signature — considered and mostly equivalent in spirit, but rejected as the concrete implementation choice because it forces every internal helper (`evaluateNode`, `describeFilter`, `ValueInput`) to carry an extra generic parameter for a distinction (which literal field names exist) that only the caller's own code needs; validating `field`/`operator` as `string` against the config's own keys at the few boundaries that matter (condition creation, URL decode) keeps the internal functions simpler while a caller's own `employeeFieldConfig` can still be written with literal keys and checked with `satisfies FilterFieldConfig<Employee>` for full compile-time safety at its own definition site.

## 24. Employee-specific configuration and table rendering relocated outside the feature (FR-040, User Story 15)

- **Decision**: `fieldConfig.ts`'s Employee-specific entries (operator lists, `describe` phrases, the country/month option lists) and `validation.ts`'s Employee-specific Zod schemas merge into one new file, `src/data/employeeFieldConfig.ts`, exporting `employeeFieldConfig: FilterFieldConfig<Employee>` — each operator's `match` function now contains the logic that used to live in the engine (e.g. `hireDate`'s `day_is`/`month_is`/`year_is` string-slicing from §8, `salary`'s numeric comparison, `country`'s equality/negation). `EmployeeTable.tsx` and `format.ts` (Employee-specific table rendering and cell formatting, FR-019/FR-020) move alongside it into `src/data/`, since neither is part of what Story 15 requires to be reusable (FR-039 names "engine... condition/group components, and validation," not table rendering) and both already reference `Employee`/`Country` directly. `App.tsx` composes the pieces: `<FilterBuilder fieldConfig={employeeFieldConfig} data={employees}>{(matchingRows) => <EmployeeTable employees={matchingRows} />}</FilterBuilder>`.
- **Rationale**: FR-040 requires the Employee table's behavior to keep working exactly as before, "driven by an Employee-specific field configuration now passed into the generalized component/engine from outside the feature's internal files" — `src/data/` is that "outside," and it's already the project's home for Employee-specific data (`employees.ts`), so adding the Employee-specific config and presentation next to it is "one more of an existing thing" (Constitution I) rather than a new top-level directory. `FilterBuilder`'s children-render-prop keeps it generic (it renders the group editor, sentence, and match count itself, all engine-driven and field-config-agnostic of Employee specifics) while handing the actual row rendering to the caller, who alone knows how to display an `Employee` — this preserves FR-032's "pure composition" for `FilterBuilder.tsx` (still just composing hooks/engine calls and a callback, no new inline logic) while satisfying FR-039's "no Employee reference inside the feature."
- **Alternatives considered**: A new `src/features/employee-table/` mini-feature for `EmployeeTable.tsx`/`format.ts`/`employeeFieldConfig.ts` — rejected, that's a second feature-sized module for three files that already have a natural, existing home (`src/data/`) that fits their purpose (Employee-specific data and its presentation), and this project's Constitution III rejects structure introduced ahead of a real second need. Leaving `EmployeeTable.tsx` inside `filter-builder/` on the theory that "it's still part of the filter page" — rejected, it directly imports `Employee` and calls `formatSalary`/`formatHireDate`, which is exactly the kind of Employee-specific reference FR-039 requires the feature to be free of; Story 15's independent test (wiring a throwaway table's own config and data through the feature) would otherwise still be blocked by a stray Employee-typed file inside the feature folder.

## 25. `filter-builder` reorganized into `hooks/` and `components/` subfolders (FR-041, User Story 16)

- **Decision**: Inside `src/features/filter-builder/`, `useConditionRow.ts` and `useFilterUrlSync.ts` move into a new `hooks/` subfolder (with `hooks/index.ts` re-exporting both); `FilterBuilder.tsx`, `FilterGroup.tsx`, `FilterCondition.tsx`, and `ValueInput.tsx` move into a new `components/` subfolder (with `components/index.ts` re-exporting all four). `types.ts`, the generic `fieldConfig`-shape helpers (renamed/kept as needed per §23), `filterEngine.ts`, `validation.ts`, and `urlState.ts` — none of them a hook or a component — stay directly under `filter-builder/`, alongside the feature's own `index.ts`.
- **Rationale**: FR-041 only names two subfolders explicitly ("hook files under a `hooks` subfolder and component files under a `components` subfolder"); spec.md's Assumptions defer everything else ("the engine, validation, URL (de)serialization, formatting, and field configuration... left to the plan"). Leaving the non-hook, non-component files at the top level is the smaller change (Constitution III: no subfolder invented for a grouping the spec doesn't ask for) and keeps them visually adjacent to the feature's own `index.ts`, which already imports from all of them.
- **Alternatives considered**: A third `lib/` or `engine/` subfolder for `filterEngine.ts`/`validation.ts`/`urlState.ts`/`types.ts` — rejected, FR-041's acceptance scenarios only check for `hooks` and `components` subfolders existing and being complete; adding a third grouping is an unrequested structural change (Constitution III), and four files at a feature's top level alongside its `index.ts` is not the "flat folder" problem Story 16 describes (that problem was hooks and components mixed together, which this already resolves).

## 26. `useConditionRow` routes every value kind through one wrapped debounce call (FR-042, FR-043, User Story 17)

- **Decision**: `fieldConfig.ts`'s `DEBOUNCE_BY_VALUE_KIND: Record<ValueKind, boolean>` (§13/§25) becomes `DEBOUNCE_MS_BY_VALUE_KIND: Record<ValueKind, number>` — `text`/`number`/`day`/`year` → `700`, `select`/`month`/`none` → `0` — exposed as `debounceMsForValueKind(kind): number`. `useConditionRow` calls `useDebouncedCommit(condition.value, commit, debounceMsForValueKind(valueKind))` unconditionally for every condition, and `handleValueChange` becomes exactly `setLocalValue` (the hook's own setter) with no `if (debounced)` branch left — every value kind's edit goes through the identical call. `displayValue` likewise becomes `localValue` unconditionally (previously `debounced ? localValue : condition.value`), since the hook's existing re-sync behavior (§15/§19: `localValue` adopts `value` on any external change) already keeps it correct for non-debounced kinds too.
- **Rationale**: FR-042 is already satisfied by the existing `useDebouncedCommit` (§19: generic `(value, onCommit, delayMs)` signature, no filter concept in its name or shape) — no change needed there. FR-043 targets `useConditionRow`'s call site specifically: today's `if (debounced) { setLocalValue(value) } else { onChange({ ...condition, value }) }` is precisely the "separate if/else branch... choosing between calling the hook and calling `onChange` directly" FR-043 rules out. Replacing the `boolean` config fact with a `number` (the delay itself) removes the branch entirely — a `0`ms delay through the same `setTimeout`-based commit path is functionally immediate for selection-based inputs (imperceptible next-tick delay, well within SC-002's "no perceptible delay"), so the observable behavior is unchanged while the *mechanism* for every value kind becomes literally the same function call, satisfying FR-043's acceptance scenarios directly.
- **Alternatives considered**: Keeping the `boolean` flag and branching only on *which delay* to pass while still calling `useDebouncedCommit` unconditionally (e.g. `useDebouncedCommit(value, commit, debounced ? 700 : 0)`) — this is a smaller change but leaves a conditional expression inline at the call site keyed on the same config fact FR-043 wants sourced from configuration outright; using the numeric delay as the configuration value itself (no boolean, no ternary) is simpler and removes the last vestige of the distinction living in `useConditionRow` rather than in `fieldConfig.ts`. A literal `0` synchronous fast-path bypassing `setTimeout` entirely for `delayMs === 0` inside `useDebouncedCommit` — rejected, that reintroduces a branch inside the *shared* hook keyed on a magic value, which would violate FR-042's "genuinely generic" requirement in the other direction (a hook that special-cases zero is no longer a plain delay wrapper); a `0`ms `setTimeout` already behaves indistinguishably from synchronous commit at this UI's timescale.

## 27. One entry file per subfolder (FR-044, User Story 18)

- **Decision**: `hooks/index.ts` re-exports `useConditionRow` and `useFilterUrlSync`; `components/index.ts` re-exports `FilterBuilder`, `FilterGroup`, `FilterCondition`, and `ValueInput`. Every file that needs more than one hook or more than one component imports through the relevant subfolder's `index.ts` rather than each file individually — including the feature's own top-level `index.ts`, which imports `FilterBuilder` from `./components` (not `./components/FilterBuilder`), and `components/FilterGroup.tsx`, which needs both `useConditionRow` and `useFilterUrlSync`-adjacent helpers... in practice `FilterCondition.tsx` needs only `useConditionRow`, so a single-item import from `../hooks` still goes through the entry file for consistency (FR-044 doesn't carve out an exception for single-item imports; routing every cross-subfolder reference through the entry file, always, is one rule instead of "the entry file, except when there's only one thing").
- **Rationale**: FR-044 requires both directions — the subfolder's own entry file must exist and be complete (§25 already establishes this), and it must be the *only* import path used, inside or outside the feature. Applying the entry-file-always rule uniformly (not just "when 2+ items are needed") keeps this one consistent convention rather than two (Constitution I: "if the same rule is written in two files, the second one is a bug waiting to happen" — here, two import conventions for the same subfolder would be that bug).
- **Alternatives considered**: Allowing direct single-file imports when only one hook/component is needed, and requiring the entry file only once a second item is added — rejected, this is exactly the kind of conditional convention Constitution I warns against (the rule would need to be re-decided at every call site depending on how many items it currently needs, and would silently drift as a file's needs grow from one item to two without anyone revisiting its imports).

## 28. Automated test coverage strategy (FR-045–FR-048, SC-023/SC-024, User Story 19)

- **Decision**: Test files are co-located next to what they cover, not gathered into a parallel `__tests__` tree: a `*.test.ts` beside each logic module with no framework imports (`filterEngine.ts`, `validation.ts`, `urlState.ts`, plus the relocated `employeeFieldConfig.ts`/`format.ts` in `src/data/`, FR-045), and a `*.test.tsx` beside each hook and component under `hooks/`/`components/` in both `filter-builder/` and `src/hooks/` (FR-046), rendering with `@testing-library/react` and driving interaction with `@testing-library/user-event`. Debounce-dependent tests (`useDebouncedCommit`, `useConditionRow`) use `vi.useFakeTimers()`/`vi.advanceTimersByTime()` instead of real waits, so a 700ms delay doesn't cost 700ms of wall-clock test time. End-to-end specs live as flat files in `e2e/`, one per user-facing flow grouping (`filtering.spec.ts`, `nested-groups.spec.ts`, `url-sharing.spec.ts`, `hire-date.spec.ts`, `validation.spec.ts`, `mobile-layout.spec.ts`, `clear-all.spec.ts`), alongside the existing `app.spec.ts` smoke test — mirroring the flat convention `e2e/` already established rather than inventing a nested structure for seven files.
- **Reconciling FR-047's "every user story" with Stories 7, 9-13, 15-18 having no browser-driven behavior**: FR-047's literal text ("every user story's independent test... MUST have at least one corresponding automated end-to-end test") would, read in isolation, require a Playwright spec for Stories 9-13/15-18 — but each of those stories' own **Independent Test** in spec.md is explicitly a code-reading/audit exercise (quickstart.md's own text: "This story is verified by reading code, not by UI interaction"), and Story 7's alignment/visual-distinction check is a rendered-layout assertion, not a user flow. There is no browser-drivable *behavior* for an e2e test to exercise for these stories beyond what US1/US4's flows already cover when they're re-run as regression checks (quickstart.md Stories 9-13 explicitly say "re-run Story 1/4/8" to confirm no regression). FR-047's own enumerated "at minimum" list (single-condition filtering, AND/OR combination, nested-group logic, URL share/restore/fallback, hireDate component filtering, inline validation errors, mobile remove-control placement, Clear All) maps exactly to US1, US2, US3, US4, US5, US6, US8, US14 — no maintainability story appears in that list. SC-023's own wording is broader than FR-047's ("at least one **automated test** tracing back to its acceptance scenarios," not "automated end-to-end test") and is what actually governs completeness across US1-US18. Resolution: US1-US6, US8, US14 each get a dedicated Playwright spec (FR-047's concrete list, satisfied literally); US7 and US9-US13/US15-US18 satisfy SC-023 through the unit/component tests already required by FR-045/FR-046 for the files each story restructured (e.g., US9's `useDebouncedCommit.test.ts`, US10's `useConditionRow.test.tsx`, US15's genericized `filterEngine.test.ts`/`FilterBuilder.test.tsx` using a throwaway non-Employee config) plus the e2e specs' incidental re-verification of the underlying behavior each refactor was required not to change (FR-028/FR-035/FR-040 — "no previously-specified behavior changes").
- **Rationale**: Co-location keeps "which test covers this file" a one-glance answer in the same folder Stories 16/18 just organized by kind (Principle I) — a parallel `__tests__` mirror would double the navigation surface that reorganization was meant to flatten, and FR-041/FR-044 already establish `hooks/`/`components/` as the unit of organization tests should follow, not duplicate. Fake timers are the standard Vitest pattern for debounce/interval code and avoid a slow, flaky suite (Constitution III: no unnecessary real-time waits). No test-only production code is introduced anywhere in this strategy (FR-048) — every test imports the same `evaluateNode`/`validateConditionValue`/`encodeFilterToParam`/hooks/components the app itself uses, and Playwright specs drive `npm run dev`'s real server (already wired via `playwright.config.ts`'s `webServer`).
- **Alternatives considered**: A top-level `src/__tests__/` (or `test/`) tree mirroring the source structure — rejected, it's a second directory tree to keep in sync with every future file move, exactly the kind of duplicated structure Constitution I warns against, for no discoverability gain over co-location at this project's size. Literal-reading FR-047 as requiring a Playwright spec per maintainability story (e.g., a "Story 9 e2e test" that does nothing but re-run Story 1's flow under a different filename) — rejected as needless duplication of an assertion the *actual* Story 1 e2e spec already makes; SC-023's broader "automated test" wording, plus FR-047's own concrete list naming only the eight behavior-bearing stories, supports treating the maintainability stories' unit/component tests as their qualifying automated test. Snapshot testing for `FilterCondition`/`FilterGroup` layout (Story 7) — rejected, brittle against incidental class-name/whitespace changes; asserting computed grid-column count/nested-group border presence via Testing Library queries is more resilient and still verifies FR-023/FR-024 directly.
